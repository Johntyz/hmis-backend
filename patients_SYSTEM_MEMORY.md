# SYSTEM MEMORY
## SYSTEM OVERVIEW
The Hospital Management Information System (HMIS) backend is a Django REST application designed to manage patient data. This module is responsible for storing, updating, and retrieving patient information. It fits into the overall HMIS workflow by providing a centralized database for patient records, which can be accessed by authorized personnel.

The following user roles interact with this module:
- Admins: Can create, update, delete patient records.
- Receptionists: Can create, update patient records.

## COMPLETE DATA MODEL
### Patient Model
- Model name: Patient
- Exact purpose: Stores patient information.
- Fields:
  - first_name: The patient's first name. (Required, Not unique)
  - last_name: The patient's last name. (Required, Not unique)
  - date_of_birth: The patient's date of birth. (Required, Not unique)
  - gender: The patient's gender. (Required, Not unique)
    - Choices: ('M', 'Male'), ('F', 'Female')
  - phone_number: The patient's phone number. (Required, Unique)
  - email: The patient's email address. (Optional, Unique)
  - address: The patient's address. (Optional, Not unique)
  - created_at: The timestamp when the patient record was created. (Required, Not unique, Auto-generated)
  - updated_at: The timestamp when the patient record was last updated. (Required, Not unique, Auto-generated)
  - deleted_at: The timestamp when the patient record was soft-deleted. (Optional, Not unique)
- Relationships: None
- Default values:
  - created_at: Auto-generated by Django.
  - updated_at: Auto-generated by Django.
- Computed or derived fields: None
- Soft delete fields: deleted_at

## BUSINESS RULES
1. The patient's date of birth cannot be in the future.
2. The patient's phone number must contain only digits.
3. The patient's email address must be unique.
4. The patient's phone number must be unique.
5. A patient record can be soft-deleted by setting the deleted_at field to the current timestamp.
6. Only admins and receptionists can create, update, or delete patient records.
7. The patient's first name, last name, and date of birth are required fields.
8. The patient's email address and phone number must be valid.
9. The patient's address is optional.
10. The patient's record can only be updated by authorized personnel (admins and receptionists).

### Receptionist Role
- Exact actions they can perform: Create, update patient records.
- Exact actions they cannot perform: Delete patient records.
- Exact conditions that change their permissions: None
- Exactly how permissions are enforced: Through the IsAdminOrReceptionist permission class.

## STATUS MACHINES
### Patient Record Status
- All possible states:
  - Active ( deleted_at is null)
  - Deleted ( deleted_at is not null)
- All allowed transitions:
  - Active -> Deleted (through soft-deletion)
- All blocked transitions:
  - Deleted -> Active (once a record is soft-deleted, it cannot be restored)
- What happens to related data at each transition:
  - When a patient record is soft-deleted, its deleted_at field is set to the current timestamp.

## EXISTING PATTERNS & CONVENTIONS
- How ViewSets are structured: The PatientViewSet is a ModelViewSet that inherits from Django Rest Framework's viewsets.
- How serializers are structured: The PatientSerializer is a ModelSerializer that inherits from Django Rest Framework's serializers.
- How permissions are applied: Permissions are applied through the permission_classes attribute in the PatientViewSet.
- How validation is done: Validation is done through the validate methods in the PatientSerializer.
- How errors are returned: Errors are returned as a JSON response with a validation error message.
- How services are used: Services are used to encapsulate business logic and database operations.
- Any base classes or mixins used: The PatientService uses Django's ORM to interact with the database.
- URL routing conventions: URL patterns are defined in the patients/urls.py file using Django Rest Framework's routers.

## API SURFACE
### Patient Endpoints
- Endpoint: patients/
- What the endpoint does: Returns a list of patient records.
- Exact URL pattern: /patients/
- Allowed HTTP methods: GET
- Who can access it: Admins, Receptionists
- What data it expects: None
- What it returns on success: A JSON response with a list of patient records.
- What it returns on failure: A JSON response with an error message.

- Endpoint: patients/{id}
- What the endpoint does: Returns a single patient record.
- Exact URL pattern: /patients/{id}
- Allowed HTTP methods: GET, PUT, PATCH, DELETE
- Who can access it: Admins, Receptionists
- What data it expects:
  - GET: None
  - PUT, PATCH: A JSON payload with updated patient data.
  - DELETE: None
- What it returns on success:
  - GET: A JSON response with the patient record.
  - PUT, PATCH: A JSON response with the updated patient record.
  - DELETE: A JSON response with a success message.
- What it returns on failure: A JSON response with an error message.
